# 玄鑑 XUAN JIAN — 設計文件

記錄**為什麼這樣做**，以及**踩過哪些坑**。功能清單與使用說明在 [README](../README.md)。

---

## 1. 產品定位

| 項目 | 決定 | 理由 |
|---|---|---|
| 形態 | PWA（可安裝、離線可用、無後端） | 命理資料很私密，不該上傳 |
| 技術 | 原生 ES Modules + CSS，零建置、零相依套件 | 十年後還打得開；不會被工具鏈綁架 |
| 資料 | 全部存在裝置 localStorage，可匯出／匯入 JSON | 同上；使用者自己掌握 |
| 解讀 | **不內建模型**，改為產生提示詞交給外部 LLM | 解讀需要語言模型，但不該為此建後端、收資料 |
| 語言 | 繁體中文為主，提示詞可切語言 | — |

### 核心迴圈

```
本機算得出來的 ──→ 本機算（曆法、星盤、紫微、姓名、數字、卦、牌、籤）
         │
         └─→ 組成提示詞 ──→ 使用者複製 ──→ 任何 LLM ──→ 貼回來 ──→ 存成紀錄
```

這條線決定了很多事：引擎的輸出必須是**可讀的純文字**（不只是給畫面用的物件），
所以每個引擎都有一個 `toText()` 或對應的「資料積木」。

## 3. 計算引擎

全部在 `src/engines/`，純函式、無副作用、可單獨用 Node 跑測試。

### 3.1 曆法 `calendar.js`

整個專案的地基，其他引擎都依賴它。

- 儒略日 ⇄ 西曆、ΔT 修正
- 太陽視黃經（Meeus 低精度，誤差 < 0.01°）→ **二十四節氣即時求解**（牛頓法迭代）
- 月亮黃經（ELP 主要 36 項，誤差 < 0.3°）
- 朔望（Meeus 第 49 章）→ **定朔定氣農曆**：朔日為初一、無中氣置閏
- 四柱：年柱以立春為界、月柱以節為界、日柱 `(JDN+49) mod 60`、時柱五鼠遁
- 納音五行（六十甲子完整表）

> **為什麼不用查表農曆？** 常見的 `lunarInfo` 十六進位表只涵蓋 1900–2100，
> 而且我沒辦法憑記憶正確寫出 200 個數值。用天文演算法反而更短、更準、範圍更大。

### 3.2 星盤 `astro.js`

- 太陽／月亮黃經 → 星座（回歸黃道）
- 恆星時 → 上升與中天：
  `Asc = atan2(cos RAMC, −(sin RAMC · cos ε + tan φ · sin ε))`
- 等宮制十二宮、月相、元素分布
- 真太陽時校正（經度時差＋均時差）可於設定開關

### 3.2b 行星 `planets.js`

用 JPL「Approximate Positions of the Planets」的克卜勒軌道根數與百年變率（適用 1800–2050）：
解克卜勒方程 → 日心直角座標 → 減地球日心座標 → 地心 → 加累積歲差化到當日黃道。

**交叉驗證**：同一條鏈路把地球日心位置反推成太陽地心黃經，
與 `calendar.js` 完全獨立的 Meeus 太陽視黃經公式比對，1900–2050 最大差 0.61 角分 ——
恰好是光行差加章動的量級，表示整條鏈路正確。
另有四項結構檢驗（水金最大距角、火土逆行天數）皆符合公認值。

相位定義（`ASPECTS`、`aspectBetween`）放在 `astro.js`，本命盤與合盤共用同一份，
避免 astro ↔ synastry 互相 import。容許度依星體加權：日月放寬 1.15、外行星收緊 0.75。

### 3.3 紫微斗數 `ziwei.js`

- 農曆生日 + 時辰 → 命宮／身宮
- 命宮干支（五虎遁）→ 納音 → 五行局（水二／木三／金四／土五／火六）
- 起紫微訣定紫微，再排紫微系 6 星、天府系 8 星
- 祿存、擎羊、陀羅、天魁、天鉞、文昌、文曲、左輔、右弼、地空、地劫、火星、鈴星、天馬
- 年干四化；十二宮：命、兄弟、夫妻、子女、財帛、疾厄、遷移、交友、官祿、田宅、福德、父母

### 3.3b 八字旺衰 `bazi.js`

採**扶抑為主**這一派。評分四類，每一筆都可解釋：

| 類別 | 內容 |
|---|---|
| 得令 | 月支本氣與日主的旺相休囚死（旺 +3、相 +2、休 −1、囚／死 −2） |
| 得地 | 四個地支的藏干通根，本氣 1／中氣 0.5／餘氣 0.3，月支再乘 1.5 |
| 得助 | 年月時三個天干中的比劫與印 |
| 洩剋 | 天干與藏干中的食傷、財、官殺 |

調候只做**寒暖燥濕**：由月支（亥子丑寒、巳午未熱）與局中火水多寡判斷。
這是原理層面可推導的，不是查表。

> **不內建**：從格、化格、專旺格，以及《窮通寶鑑》10 干 × 12 月共 120 條調候用神。
> 各家取用差異極大，憑記憶寫出來就是假的 —— 與籤詩、爻辭同一條處理原則（見 §5）。

### 3.4 運勢 `fortune.js`

- **八字大運**：陽男陰女順排，出生到交節的天數三日折一年定起運
- **十神**：以日主為基準推算比劫食傷財官印
- **流年流月**：以立春與交節為界，五虎遁定月干
- **紫微大限**：五行局數起運、陽男陰女順行，含各大限宮干四化
- **小限**：年支定起宮、男順女逆
- 流年命宮與三方四正

### 3.5 合盤 `synastry.js`

- 西洋相位：日月升 MC 兩兩比對，合／六分／四分／三分／對分含容許度與強度
- 八字：天干五合相沖、地支六合三合六沖相刑相害自刑，日柱加權
- 紫微：命宮三方四正關係、雙方命宮互落對方哪一宮、夫妻宮命中
- 綜合契合度與自動判讀提醒

### 3.6 姓名學 `naming.js`

- 五格：天格／人格／地格／外格／總格（外格規則可切換）
- 三才配置（天人地 → 五行生剋）
- 81 靈動數完整吉凶表
- 取名推薦：給姓氏筆畫，窮舉名字筆畫組合並依五格＋三才評分排序

### 3.7 數字 `numbers.js`

- 八星數字磁場：天醫／生氣／延年／伏位／絕命／五鬼／六煞／禍害
- 手機、車牌：兩兩拆解計分＋總和 81 數吉凶（可切連續／不重疊）
- 生命靈數、幸運數字推薦、兩組號碼匹配度

### 3.8 易經 `iching.js`

- 三種起卦：三枚銅錢六擲、梅花易數時間起卦、數字起卦
- 動爻 → 之卦；另求互卦、錯卦、綜卦
- 爻名依初九／九二／上六慣例

### 3.9 塔羅 `tarot.js` ／ 求籤 `qian.js`

- 塔羅：78 張牌洗牌抽牌、正逆位、五種牌陣、逆位比例與花色集中度判讀
- 求籤：搖籤、擲筊（一平一凸聖筊、兩平笑筊、兩凸陰筊），不允就重搖

### 3.10 擇日 `daily.js`

擇日各家取用的神煞差異極大，同一天在不同通書上可能吉凶相反。
這裡只做**能明確講清楚出處**的部分，其餘交給提示詞去問外部 LLM。

- **建除十二神**：日支與月建（月支）相同者為「建」，之後依序而下。
  節後換月建，所以交節前後會出現連續兩天同一個神 —— 這與傳統通書一致，不是 bug。
  口訣「建滿平收黑，除危定執黃，成開皆可用，閉破不相當」用來定當日基調。
- **彭祖百忌**：十干十二支共 22 條。條文對應到使用者選的事項時才扣分，其餘只顯示。
- **沖煞**：日支對沖的生肖；煞方取三合局的對面（申子辰煞南、寅午戌煞北、巳酉丑煞東、亥卯未煞西）。
- **與本命的關係**：日支對本命年支（生肖）、日支的沖／六合／三合／刑／害，權重年支 1.0、日支 0.8。
- **特殊日**：交節當日、四離日（二分二至前一日）、四絕日（四立前一日）、歲破（日支沖流年支）。

評分**基準 60 分起算**，每一筆加減都連同來源標籤（建除／彭祖百忌／本命／流年）
列在畫面上，不做不可解釋的黑箱分數。

**擇時（十二時辰）**同樣只取三組短而標準的規則：

1. **黃黑道十二神** —— 以日支定青龍起點「子午起申、丑未起戌、寅申起子、
   卯酉起寅、辰戌起辰、巳亥起午」，也就是 `青龍支 = (日支 × 2 + 8) mod 12`，
   再順排青龍、明堂、天刑、朱雀、金匱、天德、白虎、玉堂、天牢、玄武、司命、勾陳。
   黃道六神為吉、黑道六神為凶。
2. **日祿與天乙貴人** —— 甲祿在寅…、甲戊庚牛羊…，落在哪個時辰就加分。
3. **時支對日支** —— 沖為破、六合與三合為吉。

> 刻意**不做**的部分：二十八宿需要一個歷史紀元錨點才能起算，各家錨點不同；
> 通書裡數十種吉神凶煞（天德、月德、受死、往亡…）各派取用不一。
> 這兩類寧可留白，由「擇日評估」模板請外部 LLM 補齊並要求它標明流派。

### 3.11 八宅 `bagua.js`

整個模組沒有任何查表，全部由八卦爻象推導。

- **本命卦**：西元年各位數相加到個位得年數，男命 `11 − 年數`、女命 `4 + 年數`，
  超過 9 減 9，得 5 者男寄坤、女寄艮。四個位數全部用到，**跨世紀不必換公式** ——
  坊間常見的「100 − 年份後兩位」只適用 1900 年代，2000 年後會算錯一格。
  年份採以立春為界的命理年（`fourPillars` 的 `yearForGZ`）。
- **遊年卦變**：本命卦與方位卦比對「哪幾爻不同」即得八星 ——
  不變伏位、上爻生氣、中下爻天醫、三爻全變延年、
  中爻絕命、上中爻五鬼、上下爻六煞、下爻禍害。
- **宅卦**：房子「坐」的那一面即宅卦，坐北朝南為坎宅。

因為是推導而非查表，可以用結構性質自我驗證（三項都通過）：

| 檢驗 | 內容 |
|---|---|
| 對稱性 | 乾命的兌方是生氣 ⇔ 兌命的乾方是生氣，64 格全對 |
| 不重不漏 | 每個命卦的八方位剛好蓋到八顆星各一次 |
| 東西四命 | 四吉方必定落在同組四卦上 —— 這是東四／西四命的**定義**，而它是從爻變規則自然長出來的 |

> 開發時手寫的對照表有 7 格與演算法不符，查證後是**手寫表錯**（它自己違反對稱性）。
> 這正是本專案偏好推導的理由。

**與數字磁場共用同一套八星**：`magnetic.js` 的 `STARS` 同時供方位與號碼使用，
所以「你的天醫方在東」與「天醫數字是 13、31、68」講的是同一件事。

> 所有結果一律標示推算方式與「僅供參考」。

## 4. 提示詞產生器

這是這個 App 和一般命理程式最大的差別，設計原則是**夠自由**。

1. **資料積木**：每個引擎算完的結果註冊成一個資料區塊（基本資料、八字、星盤、紫微、
   大運流年、姓名、生命靈數、號碼），使用者勾選要帶哪些。
2. **模板**：18 個內建（命盤總覽、流年、感情、事業、紫微逐宮、日月升、八字格局、
   姓名診斷、取名、查筆畫、號碼顧問、解卦、解牌、解籤、查籤詩原文、合盤、自由問答、空白），
   全部可複製成自訂模板編輯。
3. **變數系統**：`{{data}} {{bazi}} {{ziwei_table}} {{luck}} {{synastry}} {{divination}}
   {{question}} {{today}}…` 點一下就插入；**未知變數原樣保留**，模板不會壞掉。
4. **輸出控制**：語言、語氣、深度、長度、格式、免責聲明，另有全域前綴／後綴。
5. **完全自由模式**：空白編輯器 + 變數面板，等於一個小型 prompt IDE。
6. **一鍵複製 → 外部 LLM → 貼回**：貼回的文字存成紀錄，附帶當時的模板與資料快照。
7. **模板可攜**：下載 JSON、複製分享碼（`XJTPL1:` 前綴的 base64 純文字）、匯入。

### 聚焦項目

功能頁的細節抽屜按下「深問這一項」→ 把該項完整資料寫進 `drafts.focus`
→ 跳到 `#/prompt?t=<模板>&focus=1`。

組裝時，若模板本身沒有用到 `{{focus}}`，會把它插在
「────────────\n輸出要求」**之前**而不是附在最後 ——
附在指示後面會被埋掉，插在前面才會被當成主軸。
這與 `{{question}}` 的「不讓它憑空消失」是同一種處理。

### 對 LLM 的誠實要求

涉及引用經典原文的模板（解卦、查籤詩原文、查康熙筆畫）都**明確寫入禁止杜撰**：

> 沒有把握的籤請把 lines 留成空陣列，不要自行創作或憑印象填寫。寧可缺，也不要給錯的經文。

### 法器為什麼是自己畫的

求籤與卜卦原本是幾個 div：一個圓圈當銅錢、一個圓角方框當籤筒。
能用，但跟塔羅那一頭的精緻度差太多。

先去找過免費素材，結論是**找不到能用的**：

- **銅錢**：維基共享資源上清代銅錢的公有領域照片很多，
  但都是博物館式的紀錄照 —— 打光、角度、背景各不相同，也沒有去背。
- **籤筒、木籤**：Commons 的分類裡只有廟裡的實景快照與博物館藏品照。
- **籤詩紙**：幾乎沒有；現代宮廟的籤紙還有版權問題。
- **向量圖**：OpenClipart 上搜得到的「Chinese coin」只有兩三個，品質不明。

就算找得到，風格也對不上。這個 App 是靛黑配鎏金的線稿世界，
把真實器物的照片放進來，看起來會像型錄掉進插畫裡。
塔羅牌之所以成立，是因為它本來就是一整副風格一致的畫。

所以四件都自己畫成 SVG（`src/relics.js`），順便解決三件事：
沒有授權問題、檔案小到可以內嵌、顏色吃 `currentColor` 會跟著主題走。

兩個畫的時候踩到的點：

- **順序就是遠近。** 籤筒要先畫筒口的暗面 → 再畫籤 → 最後畫筒身蓋住籤的下半。
  順序錯了就變成「籤浮在筒前面」。
- **籤詩紙在深色主題下也是淺色的紙。** 一開始做成半透明的深色面板，
  結果它就只是「又一塊卡片」。紙是一個**物件**，不是介面的一部分 ——
  在夜裡拿著一張籤詩紙，紙本來就是亮的。
  作法是在 `.qslip__in` 裡把整組代幣重新定義一次，
  裡面的徽章、吉凶、按鈕就會自動變成紙上的樣子，不用一個一個改顏色。

### 備份：勾得出來，才擋得住

原本的匯出是「全部帶走，但保密檔案除外」。那是一個寫死的決定，
而備份其實有兩種完全不同的用途：**搬到另一台裝置**（什麼都要）、
**把檔案給別人看**（個資一個都不能帶）。同一顆按鈕做不到兩件事。

所以改成勾選，而且含個資的項目標「個資」——
要傳給別人之前，一眼就看得出該取消哪幾個。
保密檔案還是預設不帶走，要另外再勾一次：那是它當初答應過的事。

匯入也照同一份清單：先列出檔案裡有什麼、各幾筆，再選合併還是取代。
**取代是不可逆的，所以會再問一次**；預設是合併。

實作上只有一份 `EXPORT_PARTS`，匯出、匯入、畫面上的勾選框都吃它。
分開寫的話，以後加一種資料就會有人只補一邊 ——
這跟「長按選字」那個坑是同一種：列舉式的東西不能有兩份。

圖片不在備份裡。自訂牌組的圖存在 IndexedDB，一副七十八張就好幾 MB，
塞進 JSON 會變成一個誰都打不開的檔案。名冊帶得走，圖要重新匯入。

### 跳到外部 LLM：能做到哪裡

使用者問的是「複製完能不能自動打開 Gemini／ChatGPT 並直接貼進對話框」。
實際狀況（2026-09）是一半一半，寫清楚免得以後有人以為是程式沒寫好：

| | 網址帶得動提示詞嗎 |
| --- | --- |
| ChatGPT `?q=` | 瀏覽器可以 |
| Claude `?q=` | 瀏覽器可以 |
| Perplexity `?q=` | 瀏覽器可以 |
| Gemini | **不行** —— 沒有官方參數，網路上能做到的都是瀏覽器擴充在前端硬塞 |
| 任何一家的**手機 App** | **不行** —— 連結會被 App 接走，但那個參數 App 不會讀進輸入框 |

所以能做到的是：**提示詞一定先複製好**，再照設定把對方開起來；
網址帶得動就順便帶過去（省一次貼上），帶不動就靠剪貼簿。

中文在這件事上特別吃虧：`encodeURIComponent` 把一個中文字變成九個字元，
六百字的提示詞一進網址就變五千多。瀏覽器撐得住，卡關的是伺服器 ——
常見的請求行上限是 8KB。所以上限抓 6000：
大約六百中文字以內帶得過去，長的就只開首頁。
寧可少一個便利，也不要讓人拿到一段被切一半的提示詞去問。

按鈕上直接寫「直接帶過去」或「開起來自己貼」，而且是**按這一次的長度算的**，
不是寫死的標籤 —— 使用者按下去之前就知道會發生什麼。

開新分頁必須在點擊事件裡**同步**做，晚一步就會被當成彈出視窗擋掉，
所以那裡不能等剪貼簿的 Promise。

### 換自己的牌組

內建的是偉特牌（1909，公有領域）。要讓人放自己的牌，有四個決定：

**圖放 IndexedDB，不放 localStorage。**
一副 78 張就算壓過也有好幾 MB，localStorage 只有 5–10 MB 而且只能存字串 ——
塞進去會把整個 App 的設定一起搞壞。牌組的名字這種小東西才留在 localStorage。

**缺的牌補內建的。**
只換背面、或只換大牌，都成立。要求一次湊滿 79 張才能用，等於沒人會用。
所以 `srcOf(id)` 是「這一副有就用這一副的，沒有就回內建的路徑」。

**匯入時就把圖壓小。**
原圖常常是幾 MB 的掃描檔，可是牌面在畫面上最多兩百多像素寬。
在裝置上縮到寬 600px、轉成 WebP 再存。少數瀏覽器 `toBlob('image/webp')` 會回 null，
那就原檔存 —— 縮不了是小事，整個壞掉是大事。

**檔名對位收得寬，但猜不到就承認猜不到。**
`major-00`、`wands-3`、`Cups_07`、`coins14`、`聖杯10`、`權杖 3`、`愚者`、`back`、`牌背`
都認得；大小寫、底線、空白、少一個零都不影響。
檔名先 `normalize('NFC')` —— macOS 的檔名是分解形，不轉的話中文檔名會對不上。
猜不到就回 `null`，那張列成「看不出是哪一張」，使用者點格子自己指定。
**猜錯比猜不到糟**：猜不到他還能補救，猜錯了他得先發現才能補救。

兩個容易漏的地方：

- 牌背是 CSS `background` 不是 `<img>`，所以走 `--card-back` 變數，
  由 `applyBack()` 在換牌組時寫進 `<html>`。
- `createObjectURL` 不收就是記憶體洩漏，換牌組時要把上一副的全部 `revoke`。
  而且「同一副但內容改過了」要能強制重載 —— 不然 `loadDeck` 會以為已經載好而跳過，
  剛匯入的圖不會出現。

### 起卦：水晶球在抽牌頁上

一開始把起卦做在儀式裡：按下「洗牌並抽牌」之後才演。
問題是那顆按鈕本身還是一顆普通按鈕 —— 儀式感是在**按下去之後**才開始的，
可是「要不要問」這個決定發生在按下去之前。所以把球搬到按鈕的位置：
按鈕不見了，那裡就是一顆水晶球，底下寫「點擊水晶球開始占卜」。

球上有一層閃光在遊走，什麼時候閃要分裝置：

- **滑鼠**：移上去就閃（`:hover`）
- **觸控**：**按著的時候**才閃

手指沒有 hover，按住就是它的 hover。這不是兩套 fallback，是兩種輸入方式
對「我正在碰它」的定義本來就不一樣。放開、離開、被系統中斷都要把閃光收掉，
不然手指滑走之後球會一直閃。

按下去之後：兩隻手從下面伸上來合圍水晶球，右手多一個搓的動作 →
球亮、光暈在背後綻開 → 整片白光蓋滿螢幕。

手的素材**本來就是一對**：左手往右上傾、右手往左上傾，兩張直接用就都對著球。
一開始寫成「右手一律鏡射」（那是為了「只有一張素材時拿左手充數」設計的），
結果把本來就對的方向翻成反的，右手變成朝外。
現在鏡射由 `--flip` 控制，預設不翻；只有真的在拿左手充數時 JS 才加 `.is-flip`。

**白光是接力棒。** 它蓋住的那幾百毫秒，抽牌儀式在底下無聲無息地長出來，
所以中間不會看到「一個畫面消失、另一個畫面出現」的接縫。
儀式貼進 DOM、確定下一幀畫得出來之後才通知白光散
（`requestAnimationFrame` 套兩層），白光底下換掉的就是完成品。
白光也會自己在三秒後散掉 —— 不管前面出了什麼事，都不能把人卡在一片白裡面。

白光用的是帶一點金的暖白，不是純白：深色 App 裡突然閃一片純白很刺眼，
而且暖白才跟鎏金是同一個世界。

插圖不齊、動畫強度關閉、系統要求減少動態，這三種情況都不畫球，
按鈕原樣放回去。兩條路共用同一個入口函式，所以不管走哪條，都一定按得下去。

### 選牌：手指與滑鼠不是同一套

**手指：滑過去看，停住才抽。**
手指滑過扇面，底下那張跳起來 —— 那是「看」，不是「選」。
停在同一張上面超過 **0.6 秒**才真的抽出來。

為什麼不是一碰就抽：扇面只露出每張牌五、六個像素，手指又比牌寬，
滑到哪一張根本看不準。要先看得到才選得到，
所以「移動」與「決定」必須拆成兩個動作。

停住的那 0.6 秒，牌邊的金光會一路長到滿。
沒有這個回饋，牌被抽走的那一刻會像是無緣無故發生的；
有了它，使用者看得到「再一下下就好」，也知道移開就取消。
CSS 那段動畫的長度與 JS 的 `DWELL` 綁在一起，有測試比對兩邊的數字 ——
金邊長滿了牌卻還沒被抽走，比沒有回饋更糟。

手指本來就會抖，所以 14px 內不算移動，不然永遠停不滿。
換了一張、或手指真的在游移，都重新計時。

**滑鼠：點一下就收下。**
滑鼠有 hover，移過去就能預覽，沒有「看不準」的問題，
再要求停 0.6 秒只會覺得這個 App 反應慢。

兩邊共用的是**往上一甩**：按住一張牌往上拉超過門檻就收下。
手指從「刷扇面」轉成「拖著丟」的分界是往上拉 44px ——
沿著扇面滑是在看，離開扇面往上走就是要它了。

### 拖曳：往上丟，或放回牌組

原本是「滑過扇面 → 底下那張跳起來 → 放開就選它」。
加上拖曳之後：**按住一張牌，它就跟著手指走**，放開時看往哪走 ——
往上丟出去就收下，放回扇面就當沒發生。已經選走的牌往下拖，可以放回牌組。

往上丟比點一下多一個好處：手指在畫面下半部，扇面也在下半部，
點的時候手會擋住自己要看的東西；拖出來就看得見了。

判斷「有沒有丟出去」要看**相對位移**，不是畫面上的某一條絕對高度。
扇面本來就攤在畫面中段，很多牌一開始就已經在上半部 ——
用絕對線的話等於隨便碰一下都算丟出去。所以記下抓的那一點，
往上拉超過 86px（或放手時還在往上衝）才算數。

沒真的拖動就當成點一下。本來會點的人不該被迫學一個新手勢。

事件掛在整個儀式層上，不是只掛在舞台上：已經選走的牌會飛到牌位那一排，
那排在舞台上緣的外面，只聽舞台的話那幾張牌根本摸不到，也就拖不回來。
代價是要自己判斷「有沒有抓到東西」，沒抓到就讓事件照常傳下去 ——
不然關閉鍵會被 `preventDefault` 吃掉。

觸控還要多擋一件事：長按預設會跳出選取框與放大鏡，圖片也會被拖走。
水晶球與整個儀式層都攔掉 `contextmenu`，CSS 再補
`-webkit-touch-callout: none` 與 `-webkit-user-drag: none`。

插圖不進 Service Worker 的安裝外殼：`cache.addAll()` 只要有一個 404
就會讓整個 Service Worker 裝不起來。改成第一次用到才抓，
存在跟版號無關的 `xj-art` 快取，改版不用重抓 —— 跟塔羅牌圖同一套辦法。

白底的光暈在建置時就去背，不在 CSS 裡硬凹：
`mix-blend-mode: screen` 讓黑變透明，白的永遠是白的；
`multiply` 讓白變透明，但整張會跟著變暗。兩個都不對。
所以 `tools/make_ceremony.py` 一次做掉 —— 把「離白有多遠」當成 alpha，
顏色再除回去，等於把 multiply 合成反推回來。

### 為什麼「一鍵複製」要變成預設

提示詞產生器一開始是這個 App 的主角：模板、積木、自訂變數、可編輯預覽，
能調的都給調。可是實際走一遍會發現，絕大多數人進了那一頁只做一件事 ——
往下捲、按複製、離開。中間那一整頁的選項，對他們是純粹的路障。

所以 v0.20.0 把預設路徑改成：功能頁按「請 LLM 解讀」，當場用設定裡的預設值
組好、複製、跳到貼回頁。產生器沒有被拿掉，而是收進設定裡的
**「進階提示詞」**開關（預設關閉）—— 要調的人自己打開，一次設定，之後都走那條路。

這種「把進階功能藏進設定」的做法有個常見的翻車方式：
兩條路各自實作，久了就對不起來，同一個模板在兩邊給出不一樣的提示詞。
所以組裝邏輯只有一份（`src/prompt/quick.js`），產生器也從那裡拿，
並且有一個測試直接比對「一鍵組出來的」和「產生器預設組出來的」必須一字不差。

剪貼簿有個限制要遵守：寫入必須發生在使用者手勢的同一個事件裡。
所以 `askPrompt()` 全程同步 —— 不 `await`、不動態 `import`，
連功能頁上那幾十個 `<a href="#/prompt?t=…">` 也是在 `click` 當下攔下來處理的，
不是等 `hashchange` 才動作。晚一個 tick，Safari 就會拒絕寫入。

### 為什麼紀錄要能比較不同模型

這個 App 的解讀一律交給外部 LLM，所以「同一份提示詞、不同模型會給出不一樣的答案」
是結構上必然會發生的事，不是 bug。與其假裝只有一個標準答案，
不如讓使用者自己看見差異 —— 貼回時可以標註模型，之後選 2–4 筆左右滑著並排比較。

比較時會先檢查幾筆的提示詞是否相同：若不同會明講**差異可能來自提示詞本身而不是模型**，
避免使用者做出錯誤歸因。

### 3.12 語調 `wenyan.js`

App 自己寫的解釋文字有白話與淺近文言兩套，設定頁可切。

- **範圍刻意有界**：建除十二神 12、黃黑道十二神 12、八宅八星 8×2、
  數字八星磁場 8、生命靈數 12、西洋十二宮 12，共 76 條。
- **不做的部分**：塔羅牌義本來就是關鍵字不是散文；易經卦爻應引用《周易》原文，
  由本 App 改寫成文言只會變成假的經文 —— 這與 §5 的資料誠信原則是同一條線。
- **實作**：引擎以 `reg` 參數選字（`pick(表, key, 白話, reg)`），
  不直接讀設定，維持純函式；視圖從 `settings.register` 傳進去。
  `ctx()` 的快取鍵也納入語調，切換後才會重算。
- **提示詞**：組裝時附一行輸出要求，讓外部 LLM 用同一種口吻回答；
  自訂模板可用 `{{register}}`。

### 出生資料分享碼

合盤需要兩個人的資料，但這個 App 沒有帳號也沒有伺服器。
解法是把一份檔案編成一段純文字（`XJPRO1:` + URL 安全的 base64），
讓人直接貼在訊息裡傳。對方貼回自己的 App 就變成一份新檔案。

**刻意只帶推算需要的欄位**：姓名、性別、出生時間、出生地。
不帶解讀紀錄、標籤、模板或任何其他資料 —— 分享一次合盤，不等於分享整個 App 的內容。

解析失敗（亂碼、空字串、格式不符、缺出生日期）一律回傳 null 並提示，不會寫進檔案。

## 5. 資料誠信原則

這個專案反覆遇到同一個問題：**古籍文本我記不準，硬寫出來就是假的**。
處理方式統一如下。

| 情況 | 做法 | 實例 |
|---|---|---|
| 結構性、可推導 | 直接算 | 六十甲子、節氣、農曆、卦序、五格 |
| 有權威機讀資料 | 抓下來自動產生 | 康熙筆畫 ← Unicode Unihan |
| 短且高度標準化 | 內建並標示 | 81 靈動數、八星磁場、塔羅關鍵字 |
| 長篇經文、版本眾多 | **不假裝有**，改為自撰＋標示，或交給 LLM 並要求留白 | 籤詩、爻辭 |
| 需要歷史錨點或各派互斥 | **不做**，並在文件寫明為什麼 | 二十八宿、通書神煞、調候用神 |

籤詩內建的是**自撰**的「玄鑑六十籤」，介面上、文件上、提示詞裡都寫明
「非宮廟籤詩原文」，並提供匯入管道。爻辭則完全不內建，由解卦模板請 LLM 引用原文。

## 6. 視覺與動態

### 鎏金主題（v0.21.0 起）

原本是純黑白。做了六套外觀提案（`lab/skin.html`）之後改成
**「黑白＋一個金」**：深色是靛藍近黑的底配象牙白的字，淺色是米白紙配墨黑的字，
兩邊的重點色都是金 —— 深色用淡金 `#e8d9a8`，淺色用深金 `#8a6d2f`。

這是**刻意破掉原本「只有黑白」那條規矩**。理由是星辰主題配金本來就對，
而且塔羅牌背與抽牌儀式早就是這個世界的東西了。
代價是誠實的：彩度就只有這一個，不再加第二個顏色；
所有「重點」都得共用同一個金，所以金出現的地方必須克制 ——
啟用狀態、主要按鈕、工具格的圖示、首頁的干支大字、分數環，到此為止。

配套的第二個決定是**區塊不畫框**（`--edge` 永遠透明）：

- **深色靠明度差**：底 `#060810` → 區塊 `#0d1120` → 次層 `#151b2e`，三階拉開就夠了
- **淺色靠陰影**：`--lift` / `--lift-sm`，深色下兩者都是 `none`

因為深色背景上的陰影根本看不見，淺色背景上的明度差又太微弱 ——
同一種手段不可能兩邊都成立，所以兩邊本來就該用不同的手段。
`--line` 只留給真正的「線」：區段標題後那一條、表格線、格線間隙。

深色的區塊底色帶一點點透明（`#0d1120f0`），讓背後的星空若隱若現。
只透這一層，疊起來也不會糊。

### 背景星空 `starfield.js`

整個 App 底下墊一層固定的 canvas。天空本身在動，兩種疊在一起：

- **自轉** —— 整片星空朝同一個方向極慢地飄。不是每顆星各飄各的（那看起來像雜訊），
  是整片一起走，像真的天球在轉
- **視差** —— 跟著頁面捲動。每顆星有一個深度 `z`（大顆的當近景、小顆的當遠景），
  自轉與視差都乘上它，捲動時前後層次才會出來

自轉用**累積距離**而不是絕對時間：切到別的分頁再回來，中間那段不該一次補上，
不然星空會突然跳一大格。單幀最多前進 50ms —— 掉幀時自轉會慢下來，但絕不會跳。

動畫強度設為「關閉」或系統要求減少動態時，星空**還在，只是不動了**。
星辰是這個 App 的主題，該停的是動作，不是星空本身。
真的不想要的人在設定裡有一個開關，還可以調星點密度。

### 字體與圖示

- 標題 `Noto Serif TC`（明體的骨感）、內文 `Noto Sans TC`、數字 `Space Grotesk`
- 圖示是 **38 個自繪 SVG**，不使用 emoji，也不混用其他圖示庫

### 標誌

靛黑底、鎏金線：外圈虛線的**星軌**、中圈**子午線**、內圈刻度環、
中央一顆**四芒星**、正中一點**天心**，外加八方位的刻度與星點。
幾何的東西，沒有具象圖案 —— 放到 48px 還讀得出來。

同一個設計存在三個地方，各有各的理由：

| 在哪 | 做什麼用 | 為什麼不能共用 |
| --- | --- | --- |
| `assets/icons/icon.svg` | 網頁的 favicon、manifest 的向量圖示 | 要漸層、要完整細節 |
| `tools/make_icons.py` | 產生四個尺寸的 PNG | 安裝到主畫面要 PNG，SVG 不通用 |
| `icons.js` 的 `mark` | 側欄、開機畫面 | 要吃 `currentColor` 跟著主題變色，而且得簡化 |

三份沒有共用的程式，只有共用的數字（三圈半徑 160/128/88、四芒星臂長 96、
虛線 4 實 8 虛）。所以有一個測試直接去比對這些數字 ——
改了一邊忘了另一邊，測試會擋下來。

`make_icons.py` 依然**不用任何影像函式庫**（容器裡沒有 Pillow、也沒有 rsvg）：
自己算覆蓋率做反鋸齒、自己做 alpha 合成、自己寫 PNG。
畫法是「一個形狀畫一次、只走自己的外框範圍」，不是「每個像素問過所有形狀」——
後者在 512×512 要跑好幾分鐘。四芒星的距離不是把曲線切段再逐段量，
而是拿星形線的隱函數除以自己的梯度長度去估，快兩個數量級，
在一個像素的尺度上看不出差別。

maskable 版本把圖案縮到 72%、底色鋪滿不留圓角 ——
系統會自己裁成圓形或圓角，留白是留給它裁的。

### 互動狀態模型

每個可按的元素都要有這幾種狀態，而且 0.1 秒內開始反應：

| 狀態 | 表現 |
|---|---|
| 滑過 | 底色淡入；**圖示線條加粗 1.5 → 2.1**，並依語意「演一下」 |
| 按下 | 微縮 0.96 + 水波紋（按住停在滿版，放開才淡出） |
| 鍵盤聚焦 | 外框光暈，圖示同滑過 |
| 選中 | 反色實心；分段控制的色塊會**滑到**新位置 |

圖示的語意動作（`--ix` 變數，34 個各有定義）：設定轉 60°、重新整理逆轉 120°、
箭頭前進 4px、上傳往上、下載往下、星星旋轉放大、垃圾桶歪一下⋯⋯
全部只在 `(hover: hover) and (pointer: fine)` 啟用。

### 動態節奏

| 用途 | 時間 |
|---|---|
| 按下 | 120ms |
| 顏色、底色、圖示 | 200ms |
| 位移、展開、抽屜 | 320ms |
| 進場、環形描邊 | 520–800ms |

位移一律 ≤ 8px（拖曳預覽上限 26px 且有阻尼）。
設定可切「關閉／輕量／完整」，並尊重 `prefers-reduced-motion`。

### 分享長圖 `share.js`

把一份「文件描述」（一串區塊：eyebrow／title／big／h／p／kv／tags／poem／rule）
畫成黑白長圖，純 canvas，沒有任何套件。

- **兩次走訪**：第一次 `draw=false` 只累加 y 求總高，設好 canvas 高度後第二次才真的畫。
  這樣圖高永遠剛好貼合內容，不必預留空白。
- **中文斷行**：中日韓文字沒有空格可以斷，所以逐字 `measureText`。
  另外處理兩條禁則 —— 行首不可以是「，。、；：？！）》」』」，
  行末不可以是「（《「『」；碰到就把字往前收或往後推一格。
- **主題**：讀 `document.documentElement.dataset.theme`，深色模式輸出深色卡。
- **輸出**：`navigator.canShare({files})` 可用就走系統分享（iOS 可直接傳 LINE），
  否則退回 blob 下載 PNG。`ctx.roundRect` 在舊版 Safari 沒有，退回直角。

## 6.5 測試

零相依：Node 內建的 `node:test`，`node --test tests/*.test.js` 就跑，不需要 npm install。
CI 每次推送與 PR 跑一次，部署前再跑一次，沒過就不上線。

測試分三層：

| 層 | 守什麼 |
|---|---|
| **模組載入** | 每個 `src/**/*.js` 都要真的 `import()` 得起來 |
| **繪製** | 18 個頁面的 `render()` 都跑得完並吐出內容；沒有出生資料時也不能爆 |
| **引擎** | 曆法、行星、星盤、八宅、八字、擇日、姓名、數字、易經、塔羅、求籤、紫微 |

**為什麼要有模組載入這一層**：`node --check` 只驗語法，攔不住重複匯出。
實際踩過 —— `synastry.js` 同時有 `export function aspectBetween` 與
`export { aspectBetween }`，語法檢查通過，瀏覽器整頁掛掉，連帶提示詞頁打不開。

**引擎測試的三種寫法**，優先序由高到低：

1. **交叉驗證** —— 用另一條完全獨立的路徑算同一件事。
   行星鏈路反推的太陽黃經 vs. Meeus 視黃經公式，差 0.61 角分。
2. **結構性質** —— 不依賴任何外部答案。
   八宅遊年的對稱性、八星不重不漏、五行力量加總為 100%、日柱每天進一位。
3. **對照公認值** —— 最後才用。水金最大距角、火土逆行天數、立春落在 2/3–2/5。

> 刻意**不寫**逐值的快照測試：那只會把當下的輸出釘死，改個文案就紅，
> 而且不保證那個值本來是對的。

寫測試的過程抓到四個真問題：八字與方位兩頁的 `render` 讀全域狀態而不是傳入參數、
變數面板漏列十個變數、變數面板有重複項，以及我自己在測試裡寫錯的一個假設
（以為羅盤對宮一定是延年，其實延年對應的是錯卦）。

## 6.6 新手教學與安裝指引

**新手教學**用獨立的全螢幕疊層，不是底部抽屜 ——
抽屜可以往下拖關掉，第一次使用的人很容易誤觸就再也找不到。
這裡只留明確的「跳過」，另外支援方向鍵、Esc 與直接點圓點跳步。
已經有出生資料的人視同老手，不會被打擾。

**安裝指引**靠 User-Agent 判斷平台，這件事本質上不可靠，所以：

1. 能叫出 `beforeinstallprompt` 就直接叫真的安裝提示，不靠猜
2. 判斷錯的時候要有退路 —— 一定附上「其他平台的做法」讓人自己找
3. 桌面 Firefox 沒有內建安裝功能，就直說沒有，不給一組做不到的步驟

兩個容易寫錯的地方（測試有守）：

- **iPad 會謊報成 Mac**（UA 裡是 Macintosh），要用 `maxTouchPoints > 1` 補判
- **Edge 與 Samsung Internet 的 UA 裡都有 `Chrome`**，判斷順序不能錯

## 7. 實作陷阱（都是實際踩到的）

### 7.1 桌面切換功能區塊整個畫面在晃

三個原因疊在一起：

1. **View Transition 對整頁 root 拍快照** → 固定的側欄、吸頂列、底部分頁跟著位移縮放模糊。
   改成只有 `#view` 有 `view-transition-name`，其餘凍結。
2. **捲軸出現／消失** → 切到較短的頁面時版面左右跳。加 `scrollbar-gutter: stable`。
3. **View Transition 與退場動畫疊加** → 兩段動畫一起跑。支援時不加 fallback。

### 7.2 底部抽屜從右下角斜著滑進來

`.sheet` 用 `left:50% + translateX(-50%)` 置中，而開場動畫的 `from` 只寫了
`translate3d(0,100%,0)`，**把置中用的 translateX 蓋掉**，於是 X 和 Y 被同時補間。
逐幀量測：第一幀 `left=195px`，一路滑到 0。

→ 改用 `margin-inline: auto` 置中，`transform` 全部留給動畫。

連帶發現：開場用 `animation` 且 `fill-mode: both`，結束後仍持續套用、優先權高於
inline style，所以**關閉動畫根本沒播放**。改成 class 驅動的 `transition`。

### 7.3 iOS 上拖曳與捲動會抖

| 原因 | 對策 |
|---|---|
| `dvh` 隨 Safari 網址列收合持續變動，元素每幀改變尺寸 | 改用 `svh` |
| 固定滿版層用 `mix-blend-mode`，整頁每幀重新混色 | 拿掉混色，改低透明度疊加 |
| 吸頂列／底部分頁的 `backdrop-filter` 隨捲動重繪 | 觸控裝置改用高不透明底色 + `translateZ(0)` |
| `pointermove` 在觸控拖曳時也觸發，重繪整個固定漸層層 | 只在 `(hover: hover)` 啟用 |
| 滑動切頁每次 `touchmove` 重新判斷方向，手指稍偏就在水平／垂直間跳 | 超過 14px 鎖定軸向，整個手勢不再改變 |
| 慣性捲動途中起手，與瀏覽器捲動疊加 | 最近一次捲動 250ms 內不接手 |
| 螢幕邊緣與 Safari 返回手勢打架 | 左右 28px 不攔截 |
| 鎖背景捲動用 `position: fixed`，文件突然不能捲，網址列展開、視窗高度改變 | 改成擋 `touchmove`，文件捲動狀態完全不變 |
| 可編輯欄位字級 < 16px，聚焦時整頁自動放大 | 強制 `font-size: max(16px, 1em)` |

### 7.5 手機長按跳出選取框

長按一張牌、一個標籤、一顆按鈕，iOS 會跳出選取框與
「拷貝／查詢／翻譯」那一排。這是一個 App，不是一份文件 —— 從來沒人要那個。

兩件事要分清楚：

- 桌機的**右鍵選單**擋在事件上：`contextmenu` 的 `preventDefault()`。
- iOS 的**長按選取**只有 CSS 擋得住：`-webkit-touch-callout` 與
  `-webkit-user-select`。在 `contextmenu` 上 `preventDefault()` 對它完全沒用。

真正的坑不是寫錯屬性，是**寫的方式**。原本是列舉式的：
「`button, a, .tile, .card, .profile, …` 這些元件不給選」。
那種寫法永遠會漏 —— 每加一個新畫面就要記得回來補一次，
漏掉的地方就出包。抽牌儀式（`.cer`、`.cer__slot`、`.tc`）就是這樣漏掉的：
新畫面加了，那份清單沒人記得更新。

改成反過來：**整頁預設不給選，真的需要選起來複製的才開回來**
（輸入框、提示詞預覽、LLM 回覆的內文、聚焦項目的原文）。
清單從「不給選的」變成「給選的」之後，漏掉的後果從「出包」變成
「這段不能複製」——後者看得見、也不會讓人以為 App 壞了。

長文的地方本來就都有「複製」按鈕，所以關掉選取沒有真的少什麼。

`touch-action: manipulation` 是另一件事（關掉雙擊縮放的 300ms 延遲），
留在互動元件上，不要跟選字混為一談。

### 7.4 其他

- **`::after` 只有一個**：提示泡泡佔用了它，所以按鈕不能再 `overflow: hidden`
  （會裁掉泡泡）→ 水波紋移進 `.ripple-box` 裁切框，按鈕本身設 `isolation: isolate`。
- **連續開兩個抽屜**：舊抽屜的清除計時器會把新的一起清掉 → 加 `isConnected` 判斷。
- **`writing-mode: vertical-rl` 需要字型有垂直度量**：後備字型沒有時，同一欄的字會
  全部疊在一起（實測連純 `serif` 也一樣）→ 籤詩直書做成可切換、預設關閉。
- **`contain: strict` 含尺寸收斂**：套在 `position: fixed; inset: 0` 的滿版層上會出事，
  改用 `contain: layout paint`。
- **分段控制的色塊在隱藏的分頁裡量不到寬度** → 顯示後要再呼叫一次定位。
- **Service Worker 會讓使用者卡在舊版**：新版部署了，已安裝的 App 還跑著舊程式碼
  → `controllerchange` 時自動重新載入（首次安裝不觸發）。
